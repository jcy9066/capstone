# 20260429 [FULL] Raspberry Pi 명령 통신 방식 비교

## 1. 배경

현재 프로젝트는 Raspberry Pi 4가 카메라 프레임을 GPU 서버로 전송하고, GPU 서버가 객체 탐지 및 Pose Estimation 모델을 실행하는 구조를 목표로 한다.

네트워크 방향은 다음처럼 보는 것이 현실적이다.

```text
Raspberry Pi 4 -> GPU 서버: 가능
GPU 서버 -> Raspberry Pi 4: 직접 접속은 불확실하거나 불필요
```

따라서 Raspberry Pi가 먼저 GPU 서버에 연결하고, 그 연결을 통해 영상, 상태, 명령을 주고받는 구조가 적합하다.

이 문서는 Raspberry Pi가 모터, 스피커, 카메라 설정 같은 명령을 받는 방식으로 다음 두 가지를 비교한다.

```text
1. HTTP Polling 방식
2. WebSocket 방식
```

## 2. 공통 전제

영상 전송은 별도 흐름으로 둔다.

```text
Raspberry Pi
카메라 프레임 캡처
JPEG 인코딩
HTTP POST /frame
GPU 서버
```

상태 전송도 별도 흐름으로 둘 수 있다.

```text
Raspberry Pi
CPU, 온도, 배터리, 네트워크 상태 수집
HTTP POST /status
GPU 서버 또는 관제 서버
```

이 문서의 비교 대상은 주로 명령 수신 흐름이다.

```text
수동 조종
정지 명령
속도 변경
경고음 재생
카메라 FPS/해상도 변경
순찰 모드 변경
```

## 3. 방식 A: HTTP Polling

### 3.1. 개념

Raspberry Pi가 일정 주기마다 GPU 서버에 명령이 있는지 물어본다.

```text
Raspberry Pi -> GPU 서버
GET /commands?robot_id=pi-01

GPU 서버 -> Raspberry Pi
{"command":"forward","speed":0.4}
```

명령이 없으면 서버는 빈 응답을 돌려준다.

```json
{"command": null}
```

### 3.2. 예시 흐름

```text
1. 관리자가 웹 대시보드에서 전진 버튼을 누른다.
2. GPU 서버 또는 관제 서버가 pi-01의 다음 명령을 forward로 저장한다.
3. Raspberry Pi가 /commands를 호출한다.
4. 서버가 forward 명령을 응답한다.
5. Raspberry Pi가 모터를 전진 방향으로 제어한다.
6. 다음 polling에서 stop 또는 다음 명령을 받는다.
```

### 3.3. 장점

- 구현이 쉽다.
- HTTP API만 있으면 되므로 디버깅이 단순하다.
- `curl`로 바로 테스트할 수 있다.
- 연결이 끊겨도 다음 요청에서 자연스럽게 복구된다.
- 서버가 Raspberry Pi IP를 몰라도 된다.
- Raspberry Pi가 NAT나 방화벽 뒤에 있어도 동작하기 쉽다.
- 초기 프로토타입에 적합하다.

### 3.4. 단점

- 명령 반응이 polling 주기에 묶인다.
- 예를 들어 0.1초마다 polling하면 최악의 경우 약 0.1초를 기다린 뒤 명령을 받는다.
- 명령이 없어도 계속 HTTP 요청이 발생한다.
- polling 주기를 너무 짧게 잡으면 서버 요청 수가 늘어난다.
- 수동 조종처럼 즉각성이 중요한 기능에서는 지연이 체감될 수 있다.
- 여러 대 로봇이 동시에 접속하면 불필요한 요청 수가 증가한다.

### 3.5. 예상 지연

0.1초 polling 기준:

```text
polling 대기 지연: 평균 약 50ms, 최악 약 100ms
HTTP 왕복 지연: 약 5~30ms 이상
Raspberry Pi 처리 지연: 약 1~10ms
모터 반영 지연: 수 ms~수십 ms
```

실제 체감 지연은 네트워크와 구현 상태에 따라 다음 정도로 예상한다.

```text
평균: 약 60~100ms
최악: 약 120~200ms 이상 가능
```

### 3.6. 적합한 용도

```text
순찰 모드 변경
정지/재시작 같은 저빈도 명령
카메라 설정 변경
스피커 경고음 재생
초기 프로토타입
```

수동 조종에도 사용할 수는 있지만, 낮은 latency가 중요하면 WebSocket이 더 적합하다.

## 4. 방식 B: WebSocket

### 4.1. 개념

Raspberry Pi가 GPU 서버에 WebSocket 연결을 먼저 열고 계속 유지한다.

```text
Raspberry Pi -> GPU 서버
ws://10.108.90.21:21063/ws/robot/pi-01
```

연결이 열린 뒤에는 서버가 해당 연결을 통해 Raspberry Pi에 즉시 명령을 보낼 수 있다.

```json
{"type":"move","direction":"forward","speed":0.4}
```

중요한 점은, 네트워크 연결은 여전히 Raspberry Pi가 먼저 시작한다는 것이다.

```text
연결 시작: Raspberry Pi -> GPU 서버
명령 전달: 열린 WebSocket 연결 안에서 GPU 서버 -> Raspberry Pi
```

따라서 GPU 서버가 Raspberry Pi IP로 직접 접속하지 않아도 된다.

### 4.2. 예시 흐름

```text
1. Raspberry Pi가 부팅 후 GPU 서버 WebSocket에 접속한다.
2. 서버는 pi-01의 연결을 등록한다.
3. 관리자가 웹 대시보드에서 전진 버튼을 누른다.
4. 서버가 pi-01 WebSocket 연결로 즉시 forward 명령을 보낸다.
5. Raspberry Pi가 명령을 받자마자 모터를 제어한다.
6. 버튼에서 손을 떼면 서버가 stop 명령을 즉시 보낸다.
```

### 4.3. 장점

- 명령 전달 지연이 polling보다 낮다.
- 명령이 없을 때 불필요한 HTTP 요청을 반복하지 않는다.
- 수동 조종처럼 빠른 반응이 필요한 기능에 적합하다.
- 서버가 Raspberry Pi IP를 몰라도 된다.
- Raspberry Pi가 NAT나 방화벽 뒤에 있어도 동작하기 쉽다.
- 한 번 연결하면 양방향 메시지를 주고받을 수 있다.
- 추후 상태 heartbeat, 조종 명령, 긴급 정지 ACK 등을 같은 연결에서 처리할 수 있다.

### 4.4. 단점

- HTTP polling보다 구현이 복잡하다.
- 연결 유지, 재연결, heartbeat 처리가 필요하다.
- 서버에서 로봇별 연결 상태를 관리해야 한다.
- 네트워크가 불안정하면 끊김과 재접속 상황을 잘 처리해야 한다.
- 단순 `curl`보다 테스트가 조금 번거롭다.
- FastAPI 서버와 프론트엔드 대시보드 사이의 명령 전달 구조도 같이 설계해야 한다.

### 4.5. 예상 지연

WebSocket은 polling 대기 시간이 없다.

```text
서버 메시지 전송 지연: 네트워크 왕복/편도 지연 수준
Raspberry Pi 처리 지연: 약 1~10ms
모터 반영 지연: 수 ms~수십 ms
```

실제 체감 지연은 네트워크 상태에 따라 달라지지만, polling 방식보다 안정적으로 낮게 가져갈 수 있다.

```text
일반적인 목표: 20~80ms 수준
네트워크 불안정 시: 그 이상 가능
```

### 4.6. 적합한 용도

```text
수동 조종
긴급 정지
속도 연속 변경
카메라 방향 제어
실시간 경고음/방송 제어
운영 단계의 로봇 제어 채널
```

## 5. 두 방식 비교

| 항목 | HTTP Polling | WebSocket |
|---|---|---|
| 연결 시작 | Raspberry Pi -> 서버 | Raspberry Pi -> 서버 |
| 서버가 Pi IP를 알아야 하는가 | 아니오 | 아니오 |
| NAT/방화벽 대응 | 좋음 | 좋음 |
| 구현 난이도 | 낮음 | 중간 |
| 디버깅 난이도 | 낮음 | 중간 |
| 명령 latency | polling 주기에 영향 받음 | 낮음 |
| 명령이 없을 때 트래픽 | 계속 발생 | 거의 없음 |
| 재연결 처리 | 간단 | 별도 구현 필요 |
| 수동 조종 적합성 | 보통 | 좋음 |
| 초기 프로토타입 적합성 | 좋음 | 보통 |
| 운영 확장성 | 보통 | 좋음 |

## 6. Raspberry Pi 부하 관점

명령 polling만 보면 Raspberry Pi 4가 0.1초 주기 polling을 처리하는 것은 대체로 가능하다.

```text
0.1초 polling = 초당 10회 요청
0.05초 polling = 초당 20회 요청
```

하지만 실제 Raspberry Pi는 동시에 다음 작업을 수행할 수 있다.

```text
카메라 프레임 캡처
JPEG 인코딩
HTTP POST /frame
상태 수집
모터 제어
명령 수신
네트워크 재시도
```

이 중 Raspberry Pi에 더 큰 부담을 주는 것은 보통 명령 polling보다 카메라 프레임 인코딩과 전송이다.

따라서 명령 polling을 0.1초 미만으로 줄일 수는 있지만, latency가 핵심이면 polling 주기를 계속 줄이는 방식보다 WebSocket으로 명령 채널을 분리하는 것이 더 낫다.

## 7. 추천 설계

현재 프로젝트에는 다음 단계형 접근을 추천한다.

### 7.1. 빠른 구현 우선

```text
영상: HTTP POST /frame
상태: HTTP POST /status
명령: HTTP GET /commands polling
```

권장 설정:

```env
SERVER_BASE_URL=http://10.108.90.21:21063
ROBOT_ID=pi-01
FRAME_FPS=10
JPEG_QUALITY=70
COMMAND_POLL_INTERVAL_SEC=0.1
```

이 방식은 가장 빨리 만들고 검증할 수 있다.

### 7.2. 낮은 latency 우선

```text
영상: HTTP POST /frame
상태: HTTP POST /status 또는 WebSocket heartbeat
명령: WebSocket
```

권장 설정:

```env
SERVER_BASE_URL=http://10.108.90.21:21063
ROBOT_ID=pi-01
FRAME_FPS=10
JPEG_QUALITY=70
COMMAND_MODE=websocket
COMMAND_WS_URL=ws://10.108.90.21:21063/ws/robot/pi-01
```

수동 조종, 긴급 정지, 실시간 제어가 중요하면 이 방식을 우선 고려한다.

## 8. 최종 판단

우리 프로젝트의 현재 검증 상태는 다음과 같다.

```text
Raspberry Pi -> GPU 서버 HTTP POST 가능
GPU 서버 21063 포트 수신 가능
정지 이미지 POST 테스트 성공
다음 단계는 연속 프레임 전송과 모델 추론 연결
```

따라서 영상 전송은 HTTP POST 방식으로 유지하는 것이 적절하다.

명령 통신은 목표에 따라 선택한다.

```text
빠른 구현과 단순 검증이 목표라면:
HTTP Polling

수동 조종 latency가 중요하다면:
WebSocket
```

최종 운영 구조 관점에서는 다음 조합을 권장한다.

```text
Raspberry Pi -> GPU 서버 /frame: HTTP POST
Raspberry Pi -> GPU 서버 /status: HTTP POST
Raspberry Pi <-> GPU 서버 /ws/robot/{robot_id}: WebSocket
```

이 구조는 Raspberry Pi IP 변경에 강하고, GPU 서버가 Raspberry Pi에 직접 접속하지 않아도 되며, 수동 조종 latency도 낮게 가져갈 수 있다.
