# 모델 및 대시보드 오버레이 현재 구현 정리

작성일: 2026-05-19

이 문서는 현재 코드 기준으로 카메라 영상에 객체 탐지 결과, pose skeleton, 행동 인식 label이 어떻게 표시되는지 정리한다.

## 1. 전체 표시 흐름

현재 대시보드 영상은 프론트엔드가 직접 박스나 skeleton을 그리는 구조가 아니다. 서버가 OpenCV로 프레임 위에 시각화 요소를 그린 뒤 JPEG로 인코딩하고, 프론트엔드는 그 결과 이미지를 MJPEG 스트림으로 보여준다.

흐름은 다음과 같다.

1. 라즈베리파이 또는 스트림 입력이 서버로 프레임을 전송한다.
2. `server/app.py`가 프레임을 OpenCV BGR 이미지로 디코딩한다.
3. `process_frame_for_dashboard()`가 모델 추론과 오버레이 생성을 수행한다.
4. `publish_preview_frame()`이 오버레이가 포함된 프레임을 JPEG로 저장한다.
5. `/video_feed`가 `generate_frames()`를 통해 MJPEG로 프론트에 송출한다.
6. `frontend/templates/index.html`의 `img#camera-stream`이 `/video_feed`를 표시한다.

관련 위치:

- `server/app.py`
  - `process_frame_for_dashboard()`: 모델 결과를 기반으로 skeleton, label을 그림. bounding box 렌더링은 주석 처리됨
  - `draw_detection_overlay()`: 최신 탐지 결과를 preview frame에 다시 입히는 함수
  - `generate_frames()`: 현재 프레임을 MJPEG로 송출
  - `/api/latest_result`: 최신 탐지 결과 JSON 반환
- `frontend/templates/index.html`
  - `img#camera-stream`: 서버가 그린 영상 표시
  - `div#detection-data`: 탐지 목록 UI 영역

## 2. 현재 선택된 모델 파이프라인

현재 `.env`에서 확인된 모델 관련 설정은 다음과 같다.

```env
PIPELINE=1
STREAM_WIDTH=640
STREAM_HEIGHT=480
STREAM_FPS=15
INFERENCE_ENABLED=false
STREAM_INFER_EVERY_N=1
CUDA_DEVICE_INDEX=0
GPU_REQUIRED_FOR_INFERENCE=true
```

주의할 점은 `INFERENCE_ENABLED=false`이지만 `server/app.py`에서 `VISUALIZATION_ENABLED`의 기본값이 `true`라는 것이다. `.env`에 `VISUALIZATION_ENABLED`가 따로 없으면 다음 계산 때문에 모델이 활성화될 수 있다.

```python
MODEL_ACTIVE = INFERENCE_ENABLED or VISUALIZATION_ENABLED
```

즉, 현재 설정에서는 `INFERENCE_ENABLED=false`라도 `VISUALIZATION_ENABLED=true` 기본값 때문에 `MODEL_ACTIVE=True`가 될 수 있다.

### 2.1 GPU 전용 추론 정책

모델 추론은 CPU를 허용하지 않는다. `perception/device.py`의 `resolve_cuda_device()`가 공통으로 CUDA device를 검증하며, 다음 상황에서는 모델 로딩 전에 실패한다.

- `DEVICE=cpu`처럼 CUDA가 아닌 device가 지정된 경우
- PyTorch CUDA를 사용할 수 없는 경우
- 요청한 `cuda:{index}`가 현재 장비의 GPU 범위를 벗어난 경우

`pipeline_factory.create_pipeline()`은 1~9번 pipeline을 만들기 전에 `resolve_cuda_device()`를 호출한다. 각 detector/action 모델 생성자도 같은 검증 함수를 다시 호출하므로, pipeline 밖에서 모델을 직접 생성해도 CPU device는 허용되지 않는다.

서버 역시 `MODEL_ACTIVE=True`이면 startup 단계에서 CUDA 검증을 먼저 수행한다. CUDA 검증에 실패하면 pipeline을 로드하지 않으며, CPU fallback은 하지 않는다.

또 하나의 주의점은 프론트 제목은 `실시간 카메라 (YOLO11x-pose)`로 되어 있지만, `.env` 기준 `PIPELINE=1`은 `YOLO11n_ByteTrack_RTMPose_STGCN`이다. 실제 실행 시 환경변수로 `PIPELINE`을 다르게 넘기지 않았다면 화면 제목과 실제 모델 구성이 일치하지 않는다.

현재 pipeline 정의:

- `1`: `YOLO11n_ByteTrack_RTMPose_STGCN`
- `2`: `YOLO11x_ByteTrack_RTMPose_STGCN`
- `3`: `DINO_BotSORT_ViTPose_STGCNpp`
- `4`: `YOLO11x_BotSORT_RTMPose_STGCNpp`
- `5`: `YOLO11xPose_BotSORT_STGCNpp`
- `6`: `YOLO26m_BotSORT_RTMPose_STGCNpp`
- `7`: `YOLO26m_BotSORT_RTMPose_PoseConv3D`
- `8`: `YOLO26mPose_BotSORT_STGCNpp`
- `9`: `YOLO26mPose_BotSORT_PoseConv3D`

## 3. 어느 객체를 인식하는지

### 3.1 일반 YOLO detector

`perception/models/detector_yolo.py`의 `YOLODetector`는 현재 사람 클래스만 탐지 대상으로 둔다.

```python
PERSON_CLASS_ID = 0
self.target_classes = [PERSON_CLASS_ID]
```

COCO class 기준 `0`은 `person`이다. 따라서 일반 YOLO detector를 사용하는 pipeline 1, 2, 4, 6, 7도 현재는 사람만 탐지한다.

### 3.2 YOLO-pose detector

`YOLOPoseDetector`도 같은 `self.target_classes`를 사용한다.

```python
classes=self.target_classes
```

따라서 YOLO-pose detector를 사용하는 pipeline 5, 8, 9도 현재 사람만 탐지한다. 이 경우 탐지 결과에는 bounding box뿐 아니라 YOLO-pose의 17개 keypoint와 keypoint confidence가 함께 들어간다.

### 3.3 DINO detector

Pipeline 3의 `DINODetector`도 현재 `target_classes = [0]`으로 제한되어 있다. 따라서 DINO 기반 pipeline 역시 사람만 탐지한다.

## 4. Tracking ID와 detection 객체 구조

YOLO tracking 결과는 `detector.track(frame)`에서 list 형태로 반환된다. 각 객체는 대략 다음 구조를 가진다.

```python
{
    "id": int,
    "box": np.array([x1, y1, x2, y2]),
    "cls": int,
    "center": (cx, cy),
}
```

YOLO-pose detector의 경우 다음 값이 추가된다.

```python
{
    "keypoints": k,
    "keypoints_scores": kc,
}
```

서버는 이 정보를 다시 대시보드/API용 detection으로 변환한다.

```python
{
    "id": oid,
    "cls": cls_id,
    "box": [x1, y1, x2, y2],
    "state": state,
    "label": "",
    "score": None,
    "danger": False,
    "has_skeleton": False,
    "skeleton": None,
}
```

## 5. 색상 구분 의미

OpenCV 색상값은 BGR 순서다. 화면에서 보이는 의미는 다음과 같다.

| 코드 색상값 | 화면 색상 | 현재 의미 |
| --- | --- | --- |
| `(120, 220, 120)` | 옅은 초록색 | 기본 person의 skeleton 색상. label 없이 표시되며, 이 사람 객체에 대해서만 행동 인식을 수행 |
| `(0, 165, 255)` | 주황색 | danger가 아닌 행동 label이 붙은 사람 |
| `(0, 0, 255)` | 빨간색 | 위험 행동으로 판단된 사람. 사람 외 객체용 방어 코드에서도 사용 |

### 5.1 사람 객체

사람 객체의 bounding box는 현재 시각화하지 않는다. 기존의 70% 투명한 옅은 초록색 박스 렌더링 코드는 삭제하지 않고 `server/app.py`에서 주석 처리했다.

기본 사람 객체에는 `person #id` 같은 label을 표시하지 않는다. 다만 이 사람 객체들에 대해서만 pose/action 인식을 수행하고, skeleton이 있으면 옅은 초록색 skeleton만 표시된다.

```python
PERSON_BASE_COLOR = (120, 220, 120)
# Bounding box visualization disabled.
# PERSON_BASE_OPACITY = 0.30
label = ""
```

행동 인식 결과가 있고 `is_danger=False`이면 주황색으로 바뀌며 label이 표시된다.

```python
label = f"[{current_action['label']}] {score}%"
color = (0, 165, 255)
```

행동 인식 결과가 있고 `is_danger=True`이면 빨간색으로 바뀐다.

```python
label = f"!!! {current_action['label']} !!! {score}%"
color = (0, 0, 255)
```

### 5.2 사람 외 객체

현재 detector가 class `0`으로 제한되어 있으므로 정상 경로에서는 사람 외 객체가 탐지되지 않는다.

다만 `server/app.py`에는 `cls != 0` 객체가 들어왔을 때 `WEAPON`으로 취급하고 빨간색 라벨을 표시하는 방어 코드가 남아 있다. bounding box 렌더링은 이 경로에서도 주석 처리되어 있다. 현재 person-only detector 설정에서는 이 경로가 실행되지 않는 것이 정상이다.

## 6. Pose estimation 오버레이 여부

현재 구현은 pose estimation 결과를 화면에 오버레이한다.

사람 객체에 대해 `action_analyzer.process(frame, obj)`가 실행되고, skeleton이 반환되면 다음 요소가 그려진다.

- 각 keypoint 위치에 작은 원
- skeleton link에 해당하는 선
- 행동 label 및 score

관련 함수:

- `server/app.py`
  - `process_frame_for_dashboard()`
  - `draw_skeleton_points()`
  - `draw_detection_overlay()`
- `perception/models/action_rtmpose_stgcn.py`
  - `process()`: RTMPose로 keypoint 추출
  - `_classify()`: ST-GCN으로 행동 분류
  - `draw_skeleton()`: skeleton 표시
- `perception/models/action_yolopose_stgcnpp.py`
  - `process()`: YOLO-pose keypoint를 action model 입력으로 사용
  - `draw_skeleton()`: skeleton 표시

현재 `.env`의 `PIPELINE=1` 기준으로는 YOLO-pose가 아니라 `YOLO11n + RTMPose + ST-GCN` 조합이다. 따라서 pose keypoint는 YOLO-pose에서 직접 오는 것이 아니라, 탐지된 person box를 RTMPose에 넣어 별도로 추정한다.

## 7. 현재 행동 인식 label

현재 ST-GCN 계열 코드에서 위험 행동으로 사용하는 label은 다음과 같다.

| Action index | Label | danger |
| --- | --- | --- |
| `42` | `FALLING` | true |
| `49` | `PUNCHING` | true |
| `50` | `KICKING` | true |
| `51` | `PUSHING` | true |

분류 결과의 최대 index가 `target_actions`에 포함되면 `action_policy.py`의 두 단계 임계값으로 label을 반환한다.

```python
action = classify_target_action(max_idx, max_score, self.target_actions)
```

현재 기준은 `ACTION_SUSPICIOUS_THRESHOLD=0.20`, `ACTION_DANGER_THRESHOLD=0.50`이다. danger action이 suspicious threshold 이상이면 주황색 의심 상태로 표시되고, danger threshold 이상이면 빨간색 확신 상태로 표시된다.

단, 다른 action 파일에는 `STAGGERING`, `APPROACHING`처럼 `danger=False` label이 정의된 경우가 있다. 이 pipeline을 선택하면 주황색 표시가 사용될 수 있다.

## 8. 의심 상태 state 판정

`perception/core/trigger.py`의 `CascadingTrigger`는 객체별 `state`를 계산한다.

반환 의미:

- `0`: Normal
- `1`: Suspicious

현재 suspicious 조건은 다음과 같다.

1. 사람 bounding box의 가로/세로 비율이 `1.1`보다 큼
2. 사람 중심점 이동 속도가 `15.0`보다 큼
3. 두 사람이 125px 이내로 가까워짐

`CascadingTrigger`에는 weapon 후보 및 weapon 주변 사람을 suspicious로 바꾸는 로직도 남아 있다. 하지만 현재 detector가 사람 class `0`만 반환하므로, 정상 person-only 설정에서는 weapon 관련 조건이 실행되지 않는다.

중요한 점은 현재 `server/app.py`의 `process_frame_for_dashboard()`는 `state`를 detection 데이터에 저장하지만, `state == 0`이라고 해서 렌더링이나 행동 인식을 건너뛰지 않는다. 즉, 현재 서버 대시보드 경로에서는 모든 tracked person에 대해 pose/action 처리를 시도하지만, bounding box는 시각화하지 않는다.

반면 `perception/frame_processor.py`의 오래된 `FrameProcessor.process()`에는 `state == 0`이면 렌더링을 건너뛰는 로직이 있다. 하지만 현재 통합 서버 경로는 `server/app.py`의 `process_frame_for_dashboard()`를 직접 사용하므로 두 동작이 다를 수 있다.

## 9. 라벨 표시 방식

라벨은 `draw_overlay_label()`에서 탐지 box 좌상단 좌표를 기준으로 배경 사각형과 함께 표시된다. 이 좌표는 label 위치 계산에만 사용되고, bounding box 자체는 그리지 않는다.

기본 형식:

- 기본 사람: label 없음
- 사람 외 객체 방어 코드: `WEAPON`
- 위험 행동: `!!! FALLING !!! 87%`
- 비위험 행동: `[APPROACHING] 72%`

라벨 배경색은 해당 객체 상태 색상과 동일하고, 글자는 흰색이다.

## 10. 최신 결과 재사용 오버레이

H.264 스트림 경로에서는 모든 preview frame마다 모델을 돌리지 않고, 최신 추론 결과가 충분히 fresh하면 `render_latest_overlay()`가 최신 detection을 현재 frame 위에 다시 그린다.

관련 설정:

- `STREAM_INFER_EVERY_N=1`: n 프레임마다 추론
- `INFERENCE_MAX_RESULT_AGE_SEC`: 최신 결과를 재사용할 수 있는 시간. `.env`에 없으면 코드 기본값 `3.0`초
- `PREVIEW_MAX_FPS`: preview 송출 최대 FPS. `.env`에 없으면 `STREAM_FPS` 기준

주의할 점:

- 실제 추론이 완료된 프레임은 `process_frame_for_dashboard()`에서 그려진 오버레이를 가진다.
- 추론 사이 preview frame은 `render_latest_overlay()`가 최신 결과를 다시 그린다.
- 이 재사용 오버레이 경로에서도 bounding box는 그리지 않는다. 기본 person은 label 없이 skeleton만 표시될 수 있고, 행동 label이 있는 person은 주황색 또는 빨간색 label/skeleton으로 표시된다.

## 11. 프론트엔드 오버레이 영역

`frontend/templates/index.html`의 카메라 영역에는 다음 overlay 요소가 있다.

- `#camera-controls`: 전체화면 버튼
- `#camera-datetime`: 화면 상단 날짜/시간
- `#detection-data`: `--Now Object List--` 제목이 있는 탐지 목록 영역
- `#minimap-overlay`: 미니맵 영역

그러나 현재 `frontend/static/script.js`에는 `/api/latest_result`를 주기적으로 읽어서 `#detection-data`에 탐지 목록을 채우는 로직이 없다. 따라서 현재 skeleton과 label은 영상 프레임 내부에 그려진 것만 실제로 갱신되고, `--Now Object List--` 영역은 정적 UI에 가깝다.

## 12. 알림 및 danger 처리

위험 행동이 감지되면 다음 동작이 수행된다.

1. `detection["danger"] = True`
2. 전체 result의 `danger = True`
3. label과 skeleton이 빨간색으로 표시됨. bounding box는 표시하지 않음
4. `TelegramNotifier.send_alert_async()`가 호출됨

현재 detector는 일반 YOLO, YOLO-pose, DINO 모두 사람 class `0`만 반환하므로, 정상 설정에서는 사람 외 객체로 인한 `danger=True`가 발생하지 않는다. `cls != 0`을 `WEAPON`으로 처리하는 코드는 예외 입력에 대비한 방어 로직으로 남아 있다.

## 13. 현재 구현상 주의점

### 13.1 화면 제목과 실제 pipeline 불일치 가능성

프론트 제목은 `YOLO11x-pose`라고 표시되지만 `.env`는 `PIPELINE=1`이다. pipeline 1은 YOLO11x-pose가 아니라 YOLO11n + RTMPose + ST-GCN이다.

### 13.2 현재 detector는 사람만 인식함

일반 YOLO detector, YOLO-pose detector, DINO detector 모두 class `0`만 사용한다. 따라서 현재 설정에서는 1~9번 pipeline 모두 사람만 탐지한다.

### 13.3 pose 기반 상황 통제는 action recognizer 쪽이 적절함

사용자가 직접 정의한 n가지 상황을 통제하려면 다음 위치가 적절하다.

- RTMPose 기반 pipeline: `perception/models/action_rtmpose_stgcn.py` 또는 `action_rtmpose_stgcnpp.py`
- YOLO-pose 기반 pipeline: `perception/models/action_yolopose_stgcnpp.py` 또는 `action_yolopose_posec3d.py`

특히 keypoint 좌표와 score를 직접 검사해서 rule-based 상황을 만들려면 `process()` 이후, `_classify()` 이전 또는 이후에 별도 rule 함수를 두는 방식이 가장 명확하다.

### 13.4 state와 rendering 정책이 일관되지 않음

`CascadingTrigger` 주석에는 `0: Normal (렌더링 안 함), 1: Suspicious`라고 되어 있지만, 현재 `server/app.py` 대시보드 경로에서는 normal 객체도 pose/action 처리 대상이지만 bounding box는 표시하지 않는다. 의도적으로 의심 객체만 보여주려면 `process_frame_for_dashboard()` 안에서 `state == 0` 처리 정책을 다시 정해야 한다.

## 15. 행동 확신도 기반 skeleton 색상

행동 인식 결과는 두 단계 임계값으로 나뉜다.

```env
ACTION_SUSPICIOUS_THRESHOLD=0.20
ACTION_DANGER_THRESHOLD=0.50
ACTION_DISPLAY_TTL_SEC=1.0
```

색상 기준은 다음과 같다.

- 초록색: 사람은 탐지되었지만 target action score가 `ACTION_SUSPICIOUS_THRESHOLD` 미만인 기본 상태
- 주황색: `PUNCHING`, `KICKING`, `PUSHING`, `FALLING` 등 target action score가 suspicious threshold 이상이지만 danger threshold 미만인 의심 상태
- 빨간색: danger action score가 `ACTION_DANGER_THRESHOLD` 이상인 확신 상태

서버는 action 결과를 `ACTION_DISPLAY_TTL_SEC` 동안만 유지한다. 새 action 결과가 들어오지 않으면 stale label을 제거하고 다시 기본 초록색 skeleton 상태로 돌아간다.

## 16. Latency 개선 설정 및 배치 처리

현재 FPS/추론 관련 설정은 다음 기준으로 맞춰져 있다.

```env
FRAME_FPS=15
STREAM_FPS=15
PREVIEW_MAX_FPS=15
INFERENCE_MAX_FPS=15
ADAPTIVE_BATCHING_ENABLED=true
ADAPTIVE_BATCH_MAX_WAIT_MS=8
STREAM_INFER_EVERY_N=1
```

`raspberry/pi_client.py`는 `FRAME_FPS`, `FRAME_WIDTH`, `FRAME_HEIGHT` 값을 OpenCV 카메라 설정(`CAP_PROP_FPS`, `CAP_PROP_FRAME_WIDTH`, `CAP_PROP_FRAME_HEIGHT`)으로도 요청한다. 단, 실제 FPS 상승은 카메라 드라이버, 노출 시간, USB/CSI 대역폭, JPEG 인코딩 비용, 네트워크 상태가 허용하는 범위 안에서만 가능하다.

서버 추론 경로는 최신 프레임 우선 정책을 유지한다. 새 프레임이 들어오면 기존 대기 프레임을 덮어쓰고 `dropped`를 증가시킨다. 따라서 backlog를 쌓아 GPU 사용률만 올리는 대신, 오래된 프레임을 버리고 최신 프레임 기준 latency를 낮추는 방향이다.

`ADAPTIVE_BATCH_MAX_WAIT_MS=8`은 inference worker가 추론 직전에 최대 8ms 동안 더 최신 프레임을 받을 기회를 주는 설정이다. 이 값은 너무 크면 latency가 늘고, 너무 작으면 최신 프레임 병합 효과가 줄어든다.

Pose/action 처리에는 `process_many()` 경로가 추가되었다.

- RTMPose/ViTPose 계열: 한 프레임의 person bounding box들을 모아 `inference_topdown()`을 한 번 호출한다.
- YOLO-pose 계열: detector가 이미 제공한 person keypoint들을 한 번에 수집해 action buffer에 반영한다.
- 기존 `process()` 함수는 fallback으로 남아 있다.

현재 action model의 최종 `inference_recognizer()` 호출은 기존 MMAction wrapper의 단일 샘플 API를 유지한다. 즉, pose 추정과 action buffer 업데이트는 batch화되었고, action classifier의 완전한 tensor batch 추론은 별도 MMAction data pipeline 재구성이 필요하다.

추가로 `/api/stream_status`에서 최근 추론의 단계별 시간을 확인할 수 있다.

- `inference_last_detector_ms`: detector/tracker 단계 시간
- `inference_last_trigger_ms`: trigger state 계산 시간
- `inference_last_action_ms`: pose/action batch 처리 시간
- `inference_last_render_ms`: skeleton/label 렌더링 시간
- `inference_last_adaptive_wait_ms`: 최신 프레임 우선 adaptive wait 시간
- `inference_last_person_count`: 최근 추론 프레임의 person 수
- `inference_last_detection_count`: 최근 추론 프레임의 detection 수

이 값들을 보면서 `ADAPTIVE_BATCH_MAX_WAIT_MS`, `INFERENCE_MAX_FPS`, `FRAME_FPS`를 조정한다. latency가 커지면 adaptive wait를 줄이고, GPU가 계속 놀고 프레임 입력 여유가 있으면 카메라 FPS와 inference FPS를 같이 올린다.
